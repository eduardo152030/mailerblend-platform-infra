## Decisiones propuestas

- `services/infra-composable-crm/compose/crm-ui/` será el Compose neutral. El código conserva su nombre `crm-core-main` dentro. Imagen multietapa con un gestor/lockfile canónico, base versionada, servidor estático con fallback SPA y healthcheck; release desplegado por digest. Proponer hostname dedicado sujeto a titularidad DNS, certificado y rutas confirmadas. Servir la API desde el mismo origen mediante proxy autenticado y upstream privado. Mantener los contratos de ingestión e integraciones y proteger accesos alternativos; ningún secreto en Vite.
- Elegir un proveedor de identidad soportado. Supabase Auth es candidato si se provisiona explícitamente y se valida el flujo completo; PostgreSQL por sí solo no lo aporta. Identificar cuentas activas, deshabilitadas y roles por los tres proyectos, servicio vs. humano y responsables. Propuesta de invitar o forzar restablecimiento a cuentas aprobadas, sin transferir hashes ni sesiones. Incorporar solo identidades/roles necesarios, auditar correspondencia y conservar acceso legacy durante transición.
- Convivencia controlada en rutas distintas. Un único canal activo de escritura por flujo durante UAT y corte cuando exista riesgo de duplicar automatizaciones. Rollback por proyecto a su URL antigua y release/configuración previos sin restaurar PostgreSQL sobre escrituras nuevas. Ensayar en entorno aislado, medir tiempo de recuperación y pactar ventana/umbrales; ante fallo de auth, errores de contrato, escrituras duplicadas o pérdida de alertas, detener el avance y revertir el enrutamiento/flag mediante receta versionada. Exportar y ensayar restauración de configuración y datos internos legacy antes del primer corte, incluyendo imágenes, montajes y volúmenes; conservar copias privadas verificadas durante la ventana acordada.
- Orden propuesto: NT_Crm_FormEntries → Smart management → NT_LinkedIn Stealth Sourcing. Confirmar el mapa de rutas/funciones con el propietario. Cada proyecto requiere PASS, rollback ensayado y UAT aprobada antes de habilitar el siguiente. DDD por responsabilidad de negocio, con transporte y primitivas visuales compartidos. Extraer subresponsabilidades cohesivas cuando proceda.
